# Dota 2 Match Coach v2 — дизайн быстрого надёжного релиза

## Цель

Улучшить существующий `dota2-match-coach`, сохранив работающий сбор данных из OpenDota, STRATZ и Valve, но исправив определение линии, добавив человекочитаемые сущности, структурированный анализ всех смертей, более точные границы допустимых выводов и сбалансированный пользовательский отчёт.

## Выбранный подход

Используется точечная версия 2 существующего runtime. Интеграции с источниками не переписываются. Слой после получения ответов разделяется на небольшие тестируемые компоненты, а промежуточный JSON получает новую схему.

Полная перестройка анализатора и набор минимальных несвязанных патчей отклонены. Первая создаёт лишний риск и срок, вторая продолжает раздувать `normalize.mjs` и `report.mjs`.

## Обязательные ограничения

- Анализируется только матч на последнем точном подпаче Dota 2.
- Поддержка старых патчей не входит ни в этот релиз, ни в будущий roadmap навыка.
- Вижен, варды, smoke, объекты и личный baseline не входят в этот релиз.
- Существующие OpenDota, STRATZ и Valve-клиенты сохраняются, если изменение не требуется для полных данных десяти участников.
- Старые JSON-артефакты не мигрируют: они промежуточные и могут быть собраны заново.
- Новые runtime-зависимости не добавляются; тесты используют встроенный `node:test`.
- Без подтверждающих данных нельзя утверждать намерение игрока, состояние обзора или готовность чужих способностей.

## Текущие проблемы, которые решает v2

1. PowerShell-команда с `-Hero` и GNU-подобными дополнительными параметрами ошибочно пытается преобразовать параметр тайм-аута в account ID.
2. Текущий `lane.opponentHeroIds` записывает всю вражескую команду вместо реальных соперников на линии.
3. Артефакт хранит многие hero, ability и item значения только как числовые ID.
4. Общий критерий готовности событий слишком широкий и разрешает интерпретацию эпизода без достаточного тактического контекста.
5. Смерти присутствуют как события, но не собираются в отдельные доказательные окна и повторяющиеся наблюдаемые паттерны.
6. Стандартный отчёт чрезмерно управляется формой и не выводит анализ смертей на первый экран.
7. Обращение во втором лице возможно даже тогда, когда пользователь назвал только героя и не сообщил, что матч принадлежит ему.
8. В каталоге навыка нет воспроизводимого набора модульных и интеграционных тестов.

## Архитектура

Новый поток данных:

```text
сбор источников
  -> проверка и безопасная нормализация
  -> разрешение сущностей
  -> нормализация десяти участников
  -> определение линии и соперников
  -> нормализация событий
  -> построение контекстов смертей
  -> вычисление доступных уровней выводов
  -> JSON v2
  -> детерминированный evidence Markdown
  -> пользовательский coaching review
```

### Ответственность модулей

- `scripts/lib/normalize.mjs` остаётся оркестратором общей нормализации и больше не содержит всю предметную логику.
- Новый `scripts/lib/entities.mjs` разрешает hero, ability и item ID в проверенные названия с безопасным fallback.
- Новый `scripts/lib/lane.mjs` нормализует позиции, линии и фактических соперников выбранного игрока.
- Новый `scripts/lib/deaths.mjs` строит доказательные окна смертей и наблюдаемые признаки.
- Новый `scripts/lib/capabilities.mjs` определяет, какие классы выводов разрешены имеющимися данными.
- `scripts/lib/report.mjs` проецирует готовый артефакт и не восстанавливает игровые факты самостоятельно.
- `scripts/analyze-match.mjs` сохраняет роль координатора источников, baseline и записи артефактов.
- `scripts/analyze-match.ps1` получает явные PowerShell-параметры для тайм-аута и output directory и формирует однозначный массив аргументов Node.

## Схема артефакта v2

Существующие верхнеуровневые разделы сохраняются там, где это возможно. Версия схемы увеличивается. Добавляются или расширяются следующие структуры.

### Участники

```text
participants[]
  accountId
  hero { id, name }
  side
  position
  lane
  role
  rank
  playbackAvailable
```

Массив содержит все десять мест матча. Отсутствующее значение равно `null`, а не подменяется догадкой.

### Выбранный игрок

`player.heroId` сохраняется для совместимости внутри runtime, а рядом добавляется `player.heroName`. В пользовательском отчёте используется имя.

### Линия

```text
lane
  selectedLane
  opponents[] { accountId, hero { id, name }, position, role }
  status
  reason
```

Соперник допускается в `opponents` только при противоположной стороне и совпадающей валидной линии STRATZ. Нормальная линия может содержать от одного до трёх реальных соперников. Ноль кандидатов, больше трёх кандидатов, конфликт источников или отсутствие lane data дают неизвестный matchup с безопасной причиной. Все пять врагов никогда не используются как fallback.

### Разрешённые сущности

Hero, ability и item ссылки имеют форму `{ id, name }`. При недоступном справочнике числовой ID сохраняется, `name` равен `null`, а предупреждение не содержит сырой ответ источника.

Приоритет справочников:

1. текущие Valve-совместимые константы, уже используемые runtime;
2. OpenDota constants и таблицы ID;
3. безопасный неизвестный ID без ручного угадывания.

## Анализ смертей

### Окно события

Для каждой смерти выбранного игрока создаётся окно от 15 секунд до смерти до 5 секунд после неё.

```text
deathAnalysis.contexts[]
  time
  position
  killerHero { id, name }
  killingAbility { id, name }
  killingItem { id, name }
  timeDead
  teamfight
  nearbyAllies[]
  nearbyEnemies[]
  ownAbilityUses[]
  ownItemUses[]
  recentReposition
  nearbyDeaths[]
  nearbyKills[]
  observations
  unavailable
```

Для позиции участника берётся ближайшая запись не позднее момента смерти с максимальным допустимым возрастом 3 секунды. Если запись старее или отсутствует, близость этого участника неизвестна.

Радиус близости равен 20 minimap cells, что соответствует примерно 1 200 игровым единицам на нормализованной карте. Расстояние считается евклидово по нормализованным координатам.

### Наблюдаемые признаки

Runtime может установить следующие признаки:

- `isolated`: позиции доступны для всех живых участников; рядом нет союзника и находятся не менее двух противников;
- `afterConfirmedTeleport`: смерть наступила не позднее 15 секунд после перемещения с подтверждённой причиной `teleport item`;
- `firstAlliedDeathInFight`: смерть является первой смертью стороны игрока внутри валидного OpenDota teamfight interval;
- `tradedLocally`: вражеская смерть произошла в пределах 10 секунд до или после и в пределах того же радиуса близости;
- `ownDefensiveItemUsed`: в последние 5 секунд подтверждено применение собственного защитного предмета из именованного allowlist;
- `contextIncomplete`: хотя бы одна обязательная позиция или временная линия для признака отсутствует.

Allowlist первого релиза: Force Staff, Hurricane Pike, Glimmer Cape, Ghost Scepter, Eul's Scepter of Divinity, Wind Waker и Black King Bar. Пассивные срабатывания вроде Aeon Disk сюда не входят, поскольку `itemUsedEvents` не доказывает их готовность или момент срабатывания.

`false` означает, что условие было проверено и не выполнено. Непроверяемое условие равно `null`, а не `false`.

### Паттерны

Паттерн этой игры появляется, когда не менее двух смертей имеют одинаковую непустую комбинацию подтверждённых наблюдаемых признаков. Это не называется постоянной привычкой игрока.

```text
deathAnalysis.patterns[]
  signature
  times[]
  count
  representativeDeathTime
```

Репрезентативная смерть выбирается по максимальному `timeDead`, затем по более позднему timecode.

### Приоритетная смерть

Пользовательский отчёт выбирает смерть в таком порядке:

1. представитель крупнейшего повторяющегося паттерна;
2. смерть внутри подтверждённого переломного окна;
3. смерть с максимальным `timeDead`, при равенстве — более поздняя.

### Граница вывода

Для каждой смерти отчёт разделяет:

1. подтверждённые факты;
2. поддерживаемую гипотезу с уровнем уверенности;
3. недоступные причины.

Формулировки о намерении, обзоре, готовности чужих кулдаунов, возможности гарантированно спастись или правильности конкретного нажатия запрещены без соответствующих данных. Применение защитного предмета подтверждает факт использования, но не направление, цель и правильность применения, если источник их не предоставляет.

## Уровни доступных выводов

Вместо одного широкого события runtime хранит независимые возможности:

- факты scoreboard;
- агрегаты стадий;
- полный драфт;
- релевантный peer baseline;
- временная линия событий выбранного игрока;
- позиции десяти участников;
- тактический контекст смертей;
- повторяющийся паттерн смертей.

Каждая возможность открывается только своими минимальными данными. Наличие координат или одного ability event само по себе не открывает тактическую причину смерти.

## Пользовательский отчёт

Стандартный режим — сбалансированный, ориентир 500–900 слов.

### Первый экран

Пять коротких блоков без таблицы:

1. матч;
2. главный вывод;
3. смерти;
4. переломный момент;
5. упражнение.

Главный вывод выбирается в таком порядке:

1. доказуемый повторяющийся паттерн смертей;
2. крупнейшее релевантное отклонение от peer mean;
3. подтверждённое событие, изменившее личную эффективность игрока.

### Нижняя часть

- одна таблица максимум с двумя наиболее важными стадиями;
- компактный список остальных смертей;
- драфт, конкретная задача героя и предметы;
- ограничения данных только тогда, когда они меняют доступные выводы.

Все смерти учитываются. Одна приоритетная смерть раскрывается подробно. Повторяющиеся смерти группируются с перечислением timecodes. Уникальные смерти остаются отдельными компактными строками. Если строк больше пяти, после пяти наиболее информативных строк оставшиеся timecodes перечисляются одной строкой без выдуманной интерпретации.

### Язык и обращение

- Язык следует последнему содержательному сообщению пользователя.
- При выборе только по герою используется нейтральное «игрок на <hero>».
- Второе лицо допустимо лишь при явном сообщении пользователя, что матч принадлежит ему.
- Имена героев, способностей и предметов не переводятся и не заменяются ID.
- Внутренние названия схемы и возможностей не показываются.
- Числовая цель упражнения берётся только из готового baseline comparison с указанием минуты и размера выборки.

## Обработка ошибок

- Без STRATZ runtime продолжает разрешённый OpenDota-анализ, но не создаёт тактический контекст смертей из отсутствующих позиций.
- При частичном playback недоступные элементы каждого death context остаются `null` и перечисляются в `unavailable`.
- Неизвестная линия не угадывается по общим свойствам героя.
- Неизвестное имя сущности не останавливает сбор и не заменяется предположением.
- Старый подпач возвращает существующий безопасный отказ и не создаёт успешный артефакт.
- Для временных сетевых ошибок сохраняется безопасный статус источника; агрессивные параллельные повторы не добавляются.
- Сырые ответы, заголовки и секреты не записываются в артефакты или сообщения.

## Тестовая стратегия

Используется `node:test` без новых npm-пакетов. Тесты работают на небольших обезличенных фикстурах и не требуют токена или сети.

### Модульные тесты

- разрешение известных и неизвестных hero, ability и item ID;
- точное определение противоположной стороны и совпадающей линии;
- отказ от fallback на пять вражеских героев;
- нормализация отсутствующих position, lane и playback values;
- выбор ближайшей допустимой позиции участника;
- границы окна `-15/+5`;
- `isolated`, `afterConfirmedTeleport`, `firstAlliedDeathInFight`, `tradedLocally` и неизвестное состояние признака;
- группировка одинаковых непустых signatures;
- выбор representative и priority death;
- независимые возможности выводов;
- запрет вывода недоступной причины в проекции evidence.

### Интеграционные тесты

- полный матч с десятью участниками и несколькими смертями;
- отсутствующий STRATZ token;
- частичный replay/playback;
- неоднозначный hero selector;
- конфликт hero и account ID;
- старый подпач;
- корректное формирование PowerShell-аргументов для hero и account ID;
- структурные инварианты сбалансированного Markdown без привязки к точной литературной формулировке.

### Live smoke-test

Опциональный сетевой тест принимает текущий публичный match ID через переменную окружения. В репозитории нет постоянно зашитого match ID, который станет старым после смены патча.

## Критерии готовности

Релиз считается готовым, когда одновременно выполнено следующее:

1. Документированные Windows-команды по hero и account ID корректно передают все параметры.
2. JSON v2 содержит десять участников с доступными именами.
3. Соперники на линии определены по совпадающей линии либо matchup честно неизвестен.
4. Каждая смерть выбранного игрока учтена и получает доступный фактический контекст.
5. Повторяющиеся непустые signatures объединяются в паттерн этой игры.
6. Неподтверждённые причины не выдаются за факты.
7. Первый экран содержит пять утверждённых блоков.
8. Остальные смерти присутствуют в компактной части отчёта.
9. Старые патчи стабильно отклоняются без успешного артефакта.
10. Все модульные и интеграционные тесты проходят.
11. Live smoke-test на актуальном матче создаёт полный артефакт без регрессии существующего baseline и источников.

## Изменения инструкций навыка

- `SKILL.md` сохраняет только назначение, обязательный runtime-путь, ключевые инварианты и маршрутизацию к references.
- `references/runtime.md` документирует схему v2 и новые Windows-параметры.
- `references/source-policy.md` сохраняет и уточняет границы доказательности.
- Новый `references/death-analysis.md` содержит модель окна, признаки и правила формулировки.
- `references/review-template.md` заменяет жёсткий первый экран утверждённым сбалансированным форматом.
- `agents/openai.yaml` обновляется только при необходимости синхронизировать default prompt с нейтральным обращением и обязательным анализом смертей.

## Не входит в реализацию

- ward placement, dewarding, smoke и модель обзора;
- Roshan, Tormentor, башни и другие objective decisions;
- self-baseline и сильные игроки;
- фильтр baseline по game mode, если текущий STRATZ endpoint его не поддерживает без нового источника;
- исторические патчи;
- загрузка и декодирование raw `.dem`;
- автоматическая оценка чужих cooldowns, маны, здоровья или намерения;
- миграция артефактов v1.
